# Diagnostic archive accountability

**Deliverable:** Design-analysis document. **Evidence type:** Inspected private source, executed synthetic fixtures, and a captured Windows diagnostic-export action.

## Problem

A diagnostic workflow can successfully create support archives while a later inventory fails to recognize them. If the output format changes but the inventory rules do not, the retained evidence and the reported archive count can disagree.

## Practical value

Memory Guard's private source review exposed this mismatch in diagnostic archive bookkeeping. Correct recognition helps an operator understand what evidence remains without discarding unfamiliar files or treating an inaccurate count as a reliable storage record.

The work demonstrates a useful governance principle: records about an artifact need to remain consistent with the artifact itself as its format evolves.

## Inspect the example

Open the [captured fixture result](../examples/archive-inventory.json). It is readable directly in GitHub and requires no application installation.

The October 15, 2026 fixture created two local diagnostic archives and an unrelated operator note. Against the retained earlier recognition logic, the check failed because neither current-format archive was counted. Against a separate corrected source revision, the same check recognized both archives, confirmed that both remained present, and verified that the note's contents were unchanged.

| Check | Fixture observation |
| --- | --- |
| Diagnostic archives created and retained | Two |
| Retained archives recognized by the corrected revision | Two |
| Unrelated operator note | Contents preserved |
| Retained archives | Both remained present |

These are controlled fixture observations, not customer measurements or evidence of improved application performance.

## Follow the Windows evidence

The [Windows export review](../examples/windows-export-review.json) adds a captured check from October 15, 2026. The actual diagnostic-export action ran from a separate working directory and an extraction path containing spaces, with malformed application settings present. It created diagnostic archives, preserved those settings, and correctly reported partial cached evidence rather than a successful application session.

The review also checked privacy behavior: a cached record containing a synthetic secret was excluded in full, while a separate safe startup-failure record remained available. Against the resulting archives, the earlier recognition logic counted zero and the corrected source counted two. The archive contents and an unrelated operator note were preserved.

This demonstrates three useful capabilities for information and operations work: reconcile records to retained evidence, preserve user-owned information, and distinguish incomplete capture from a healthy application. Reviewers can inspect the summary directly in GitHub; reproducing the private application's behavior is outside this document's public deliverable.

## What makes the correction useful

The source correction preserves recognition of the earlier supported archive format while admitting the added diagnostic evidence. It continues to require the expected core contents and reject incomplete or unexpected archive shapes. Related regressions cover older and current formats, missing required contents, unexpected additions, and malformed startup evidence.

Unrecognized files remain available for review. A failure to establish ownership is a reason to withhold a bookkeeping conclusion, not permission to delete evidence.

## Evidence and limitations

The original public JSON was generated by the passing source fixture rather than written as a proposed result. The Windows summary was derived from retained execution receipts and before-and-after recognition logs; its observations were rechecked for this documentation update. The retained earlier source failed the recognition check; the corrected private source passed it. Both examples used synthetic evidence and local files. The Windows check invoked only the diagnostic-export action; it did not start normal monitoring or queued work. Private source, configuration, diagnostic archives, machine details, and operational instructions are excluded from this deliverable.

A preliminary file-move fixture encountered a Windows access-denied error. The published examples therefore cover retained-file recognition, preservation, and the stated diagnostic-export checks; they do not establish relocation behavior. They also do not qualify the desktop application's normal operation, telemetry, workload execution, recovery, every newer package, or endpoint-protection compatibility. The repaired candidate remains private and is not a verified application release. A trusted diagnostic fallback when the main executable is missing or quarantined remains unresolved.
